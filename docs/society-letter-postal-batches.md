# Saved Postal Batch Approval

## Release Status

Deployed to JU September 28, 2026; see
`ju-stewardship-overview-release-2026-09-28.md`. Automatic
PDF conversion is disabled unless a private deployment-owned converter has been
provisioned and explicitly enabled. No production letters or appeals were
created while developing this workflow.

The original single-recipient finalization remains available. This extension
reuses its readiness evaluator, hierarchy, household membership checks,
appeal transport, durable receipts, and recovery rules.

## Staff Workflow

1. In Society Letters, refresh membership when needed, save recipient choices,
   and complete postal readiness checks. Review alone does not apply appeals.
2. Select ready households (up to 10). Households without a saved review or
   current passing postal checks are not selectable. If none qualify, the
   control is disabled with instructions rather than silently selecting zero.
3. Choose Word or, when configured, PDF. Start document approval and prepare
   the documents. One request prepares one document; failure leaves the saved
   draft available without reserving a letter or applying an appeal.
4. Preview and approve each complete saved document. Check all pages, names,
   address, and spacing. Recipient, template, membership, date, or policy changes
   invalidate approval. Discard an outdated draft and start again; existing
   recipient reviews are retained. A draft's letter date does not roll forward
   silently when returning on a later day.
5. Confirm the batch and its listed household members. This atomically reserves
   the approved documents in Letter history but does not yet call NXT.
6. In Letter history, confirm **Create approved letters and apply appeals**.
   One household is processed per request. Fresh NXT checks precede writes; the
   highest applicable appeal is assigned to both verified household members or
   the single constituent. Lower tiers remain covered in the app, not sent again.
7. Download the saved files after all member receipts are confirmed. Mark mailed
   separately, only after postal dispatch. No email or NXT PDF attachment is
   generated by this workflow.

Leaving the page pauses after the in-flight request. Returning never starts
writes automatically. Continue the same batch, not a new one. Any uncertain
member result pauses the whole batch until read-only verification resolves it.
The existing per-household receipt and continuation controls remain available.
An approved reservation cannot be discarded or recreated through the draft UI.

## Storage and Safety

- `stewardship_letter_postal_batches` holds draft/approved/cancelled approval
  records. A partial unique index allows only one open draft per organization
  database. Draft changes use the existing 120-second workspace lease/revision.
- `stewardship_letter_postal_documents` stores immutable base64 bytes and their
  SHA-256 digest. Documents are loaded only for previews/downloads, not with
  the workspace list. Rows contain constituent data: keep the same access,
  backup, encryption, and retention controls as the other stewardship tables.
- Every approved delivery stores the document ID, size, hash, format, and
  approval audit. Approval plus all reservations are one database statement;
  a duplicate reservation rolls back the whole operation.
- Approval and download verify the stored bytes. Appeal recovery never
  regenerates or reconverts a document. PDF conversion occurs before approval,
  before reservations, and before any NXT writes.
- Files are bounded to 4 MiB; combined downloads are bounded to 4 MiB before
  ZIP overhead. Larger batches use individual downloads. Previews are
  authenticated, same-origin, and no-store. PDF previews render pages with
  PDF.js evaluation disabled and page-count/pixel limits; they do not embed
  an active PDF document in a browser iframe.
- Preparing or continuing is bounded by the selected batch size and never
  starts on page load. NXT timeouts retain uncertain receipts without retries.
- No cron, live-query-on-load, sandbox configuration, or email behavior changes.

## Private PDF Converter Setup

This is an integration boundary, not a newly provisioned cloud service. Word
approval remains available without it. Never use a public anonymous converter
or point a sandbox deployment at a JU donor-data service.

Use a privately managed Gotenberg-compatible LibreOffice conversion service:
[official convert route](https://gotenberg.dev/docs/convert-with-libreoffice/convert-to-pdf).
Provision a supported, pinned, security-updated image behind an authenticated
HTTPS gateway. The gateway must validate the bearer token; the app setting
alone does not secure the converter. Restrict ingress, block document-triggered
outbound network access, disable unnecessary routes, limit requests and
concurrency, and delete temporary files after processing. Do not log document
bodies, tokens, or donor names. Validate data residency and retention before
using real constituents.

Set server-side environment values for the intended deployment only:

```text
SOCIETY_PDF_ENABLED=true
SOCIETY_PDF_CONVERTER_URL=https://YOUR-PRIVATE-CONVERTER/forms/libreoffice/convert
SOCIETY_PDF_CONVERTER_TOKEN=<secret gateway token>
```

Only this exact HTTPS path is accepted; redirects, URL credentials, query
strings, and fragments are rejected. The server submits one DOCX named
`letter.docx`, has a 45-second deadline and bounded streamed response, and
does not retry automatically. Converter details never appear in user errors.
Disabling the converter prevents new PDFs but does not prevent downloading
previously saved approved PDFs.

Before enabling, test with fictional letters using the actual organization
templates and installed fonts. Compare PDF line breaks, logos, address blocks,
signatures, and every page against Word. Staff must preview each saved PDF
before final approval. Native Word and LibreOffice pagination can differ;
do not promise exact fidelity without this deployment-specific check.

The current implementation does not attach PDFs to NXT, send postal mail,
or introduce a document-retention cleanup job. Plan access-controlled object
storage/retention if document volume outgrows the database approach.

## Validation

September 28: full suite passed (5,025 tests; 98 opt-in tests skipped).
The isolated PostgreSQL suite separately passed all 13 safeguards, including
immutable documents, expired-lease rejection, single-draft uniqueness, and
atomic rollback of a multi-household approval when a reservation conflicts.
Two subsequent test-only additions also passed in the page suite (39 tests)
and route suite (85 tests): sequential current revisions and exact saved PDF
download gating. Build, typecheck, release-worktree guard, and diff checks
passed.

Browser QA used local fictional documents with no production or NXT access.
PDF pages rendered before approval was enabled; batch approval stayed disabled
until both documents were approved and the separate checkbox was checked.
Word review also rendered at a 390-pixel viewport without horizontal overflow.
Opening drafts/previews moves focus into view, and closing returns focus to
the review button. Temporary servers were stopped and viewport overrides reset.

The converter adapter was tested for missing configuration, authentication,
redirect rejection, timeouts, malformed responses, and header/stream size
limits. No deployed converter has been provisioned or tested; actual template
font/pagination fidelity still needs the setup verification above.
